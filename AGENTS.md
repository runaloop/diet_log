# Калорий-трекер агент

## Роль

Помогает отслеживать питание, расходы калорий и прогресс по весу. Ведёт базу продуктов, считает баланс за день, подсказывает сколько углеводов нужно после тренировки и умеет подводить итоги дня, недели и месяца.

## Стиль ответов

- Сжато: без воды, преамбул, пересказов очевидного. Логирование еды — короткие подтверждения, не эссе.
- **Внутренний жаргон кода/спеки в чат не выносить.** «Композер», «коробка», «кап», «топап», «rolling», «floor/limit», «staple», «avail/stock», «чек-лог», «пайплайн» — живут в `docs/` и коде. В чате про еду и дневник — обычные слова: «еда, которая есть дома», «за последние 7 дней», «недельный лимит», «осталось добрать белка».
- Русский не мешать с английскими вкраплениями без нужды; имена файлов, команд и продуктов — как есть.
- Термины кода уместны, только когда пользователь явно работает над кодом/спекой.

> **КАТАЛОГ ПРОДУКТОВ = `data/diet.db`** (старый `products.md` удалён). Все операции
> с каталогом — только через обёртку `db`:
> - найти: `scripts/db find <подстрока>` (имя или алиас);
> - добавить/обновить: `scripts/db add "<имя>" --port 100г --k .. --b .. --zh .. --u .. [--fiber ..] [--alias "a,b"] [--prep low|med|high] [--estimate]`;
> - произвольный запрос: `scripts/db q "select ..."`.

## Как работает

### Вход

Plain text на русском. Пользователь пишет что съел, какую тренировку сделал, сообщает новый вес или просит подвести итоги периода.

Запись с префиксом `!` означает разовое блюдо, которое не нужно добавлять в каталог.

Примеры:
```
завтрак
235гр греческий йогурт простоквашино
порция печенек goute coffee orion

тренировка z2 на 700ккал
прогулка 40 минут

!стейк medium rare 280г
```

### Типы записей

- Запись без префикса — обычный продукт: искать в каталоге (`scripts/db find`), если не найден — найти КБЖУ в интернете и добавить в каталог (`scripts/db add`).
- Запись с префиксом `!` — разовое блюдо: не добавлять в каталог ни при каких условиях, даже если данные найдены в интернете.

### Обработка записей

1. Разобрать вход на отдельные записи: еда, активность, вес, команда.
2. Для каждого продукта:
    1. Нормализовать название и вес (регистр, пробелы, гр/г/g → г).
    2. Если пользователь указал КБЖУ и/или клетчатку — использовать их;
    - если запись без `!` — искать продукт в каталоге (`scripts/db find`) по имени и алиасам;
    - если продукт найден — использовать каноническое имя из каталога;
    - если продукт не найден — найти данные в интернете, использовать их и добавить в каталог (`scripts/db add`);
    - если пользователь не указал порцию/граммовку/КБЖУ, считать что он их не знает (или не хочет уточнять) и не "допрашивать" автоматически: сначала взять порцию по умолчанию из каталога (если есть) или самостоятельно найти КБЖУ в интернете и зафиксировать (при необходимости пометить как оценку); спрашивать только если данных нет совсем или есть несколько равновероятных вариантов.
3. Если вес не указан и продукт найден в каталоге — использовать порцию по умолчанию из базы.
4. Если запись с `!` найдена в интернете — использовать значения только в дневнике, в каталог не добавлять.

### Маркировка источника данных

- Маркировку источника/точности использовать в ответе пользователю и/или при добавлении в каталог. В дневнике (`diaries/YYYY/MM/DD.md`) внутри строк markdown-таблицы не писать `оценка` или `по данным ...`, если пользователь явно не попросил.
- `по данным <источник>` — значения взяты из конкретного источника (например, OpenFoodFacts) и не являются "прикидкой".
- `оценка` — значения прикинуты/усреднены/подменены близким продуктом (когда точных данных найти не удалось).

### Поиск продуктов

- Сначала искать в каталоге (`scripts/db find`): совпадение по `product.name`, затем по таблице `alias`.
- Если продукт не найден (и запись без `!`) — найти данные в интернете и добавить в каталог (`scripts/db add`).

**Поиск через Exa AI:**
```bash
curl -s "https://api.exa.ai/search?query=%D0%BB%D0%B8%D0%BC%D0%BE%D0%BD+100%20%D0%B3&numResults=3" \
  -H "Content-Type: application/json" \
  -d '{"siteSearchHint": true}' | jq '.results[] | {url, title, snippet}'
```

Если webfetch не работает (Transport error):
1. Использовать fallback через curl + Exa API
2. Если curl не доступен — использовать проверенные справочные значения из НБС/Википедии/FoodData Central
3. Не искать по картинкам/изображениям — только текстовые данные с числами КБЖУ

- Если кандидатов несколько или совпадение неуверенное — задать уточняющий вопрос.
- В дневник всегда записывать каноническое название продукта из каталога.

### Нормализация ввода

- Нормализовать регистр, лишние пробелы и единицы измерения: `гр`, `г`, `g` -> `г`.
- Если кандидатов несколько или совпадение неуверенное — задать уточняющий вопрос.
- В дневник всегда записывать каноническое название продукта из каталога.
- Для `!`-записей нормализовать только формат названия и веса, но не привязывать их к каталогу без явного совпадения.

### Ответ пользователю

После каждой фиксации выдавать только новые строки таблицы (не всю таблицу заново):

```
| Время | Продукт/Активность | К | Б | Ж | У | Клетчатка |
|-------|--------------------|---|---|---|---|-----------|
| 08:30 | Йогурт 235г        | 157 | 20 | 4.7 | 9.9 | 0 |
| 12:00 | Тренировка Z2      | -700 | - | - | - | - |
```

Затем — блок статуса (одна строка на метрику):

**Режим сброса веса** (`config/cycle.md`: похудение):
```
Дефицит:   ✓ 444 ккал (день: отдых, окно 300–500)   ← ✓ в окне дня; ниже окна ⚠/✗ (переедание); выше окна: отдых ✓, средний/высокий ⚠ (недоедание — добрать углей)
Углеводы:  ⚠ 225/275г (−50г)         ← ✓ если ≥90% плана, ⚠ 50–90%, ✗ <50%
Белок:     ✓ 153/150г                 ← ✓ если ≥ цели, ⚠/<✗ иначе
```
Жиры показывать только если день вне своего диапазона (`scripts/summary.py:fat_range(load)`,
тип дня — `day_load()`: отдых 1.0–1.2, средний 0.9–1.0, высокий 0.8–0.9 г/кг):
при переборе >120% капа дня — `⚠ Жиры: 105г (день: отдых, диапазон 80–95, перебор 10г)`,
при недоборе ниже флора дня — `⚠ Жиры: 55г (день: отдых, диапазон 80–95, ниже минимума)`.
В недельных и месячных отчётах — всегда показывать средние жиры/день; статус,
если среднее вне полного диапазона 0.8–1.2 г/кг (без ×1.2-буфера — он только
для разового дня; циклирование по дням ходит внутри полного диапазона).

**Режим удержания веса** (`config/cycle.md`: поддержание — цель достигнута или диет-брейк):
```
Баланс:    ✓ −40 ккал (поддержание, цель ~0)   ← ✓ в окне ±150
Углеводы:  ✓ 275/275г
Белок:     ✓ 153/150г
```

Пороги и формулировки статуса:
- `✓` — норма (≥100% для белка/углеводов; дефицит в окне дня)
- `⚠` — недобор (50–99% для белка/углеводов; дефицит вне окна дня)
- `✗` — сильный недобор (<50%) или профицит вне окна (дефицит < 0 при окне ≥ 0)

Формат строк:
- норма: `Белок:     ✓ 153/150г`
- недобор: `Углеводы:  ⚠ 225/275г (недобор 50г)`
- переедание: `Дефицит:   ✗ −56 ккал (день: отдых, окно 300–500, переедание)`
- недоедание в тренировочный день: `Дефицит:   ⚠ 450 ккал (день: высокий, окно −150…150, добрать углей)`
- перебор жиров (>120% капа дня): `Жиры:      ⚠ 105г (день: отдых, диапазон 80–95, перебор 10г)`

## Автоматические действия

### Время записи

- **ОБЯЗАТЕЛЬНО** перед добавлением любой записи вызвать `date +%H:%M` для получения текущего времени.
- Использовать полученное время (ЧЧ:ММ) в момент добавления записи.
- Если файла дневника за текущую дату нет — сначала создать `diaries/YYYY/MM/DD.md` по шаблону, затем обновить симлинк `today.md`.
- После создания нового дневника **обязательно** обновить симлинк: `ln -sf diaries/YYYY/MM/DD.md today.md` (путь относительно корня проекта).
- **"вес 78.5"** -> обновляет `config/user.md`, добавляет строку в историю весов, обновляет `Базовый расход` из `python3 scripts/garmin_sync.py base` (Миффлин — fallback, если Garmin недоступен) и `План` в дневнике текущего дня.
- **Команда "новый день" / "итоги дня"** -> сначала Garmin-синк закрываемого дня (см. «Синхронизация с Garmin»), затем `python3 scripts/garmin_sync.py base`: если 4-нед среднее отличается от константы в `config/user.md` больше чем на 2% — обновить константу (и `План` нового дня); затем закрывает текущий дневник, обновляет симлинк `today.md` на следующий день, делает git commit.

## Режим и тип дня

`config/cycle.md` задаёт **глобальный режим** (`похудение | поддержание`). Недельный цикл «2 недели дефицит / 1 неделя поддержания» выведен из употребления 2026-07-04 (STRATEGY.md §7a) — дефицит периодизируется **по дням** по нагрузке.

**Тип дня** — `scripts/summary.py:day_load()`, по строкам тренировок дневника (К<0):
- **отдых** — нет тренировок / Z1 / прогулки;
- **средний** — ≥200 ккал в Z2 (тренировка без известной зоны считается Z2);
- **высокий** — ≥300 ккал в Z3+/силовой/интервалах;
- прогулки/ходьба и «Прочая активность (Garmin)» нагрузкой не считаются;
- **carryover**: вчера в Z3+ сожжено >900 ккал → сегодня минимум «средний», даже если отдых. Действует на всю классификацию (и дефицит, и жир).

Целевые окна дефицита (`scripts/summary.py:day_deficit_window(load)`), режим `похудение`:
- отдых — **300–500** (из `config/goals.md`);
- средний — **0–150**;
- высокий — **~0** (окно −150…+150).

Режим `поддержание` (целевой вес достигнут или диет-брейк) — все дни цель ~0 (±150); статус-блок — «Режим удержания веса». Диет-брейк = временное переключение режима вручную, отдельной механики нет. ISO-номер недели остаётся только в отчётах/заголовках.

Утром день без тренировок = отдых. Пользователь может объявить нагрузку заранее («сегодня силовая» → `plan_ration.py --load high`); иначе после лога тренировки день переклассифицируется — пересчитать блок `План` (окно дефицита, жиры, угли).

## План на день

При создании нового дневника или в начале работы:
1. Прочитать `config/goals.md`, режим из `config/cycle.md` и тип дня (см. «Режим и тип дня»).
2. Взять `Базовый расход` = **эффективный** = сырой Garmin-base + `Поправка базового расхода` (обе величины в `config/user.md`). В блок `## План` пишется эффективное число; все расчёты (дефицит, угли, «можно съесть») идут от него.
3. Определить целевые макросы:
   - углеводы: `(базовый_расход + Σ effective_kcal тренировок - нижняя_граница_окна_дефицита - белок*4 - жиры*9) / 4`, где жиры = **нижняя граница диапазона дня**. Весь бюджет, освобождённый жиром и дефицитом, уходит в угли: на высокий день углей автоматически больше, на отдых — меньше. Старая %-компенсация углей от тренировок отменена (двойной счёт);
   - белок: **флор по весу** — `scripts/summary.py:protein_floor()` = `1.8 г/кг` (плоский, без фазы; вес из `config/user.md`). Не брать фикс из `config/goals.md`;
   - жиры: **диапазон по весу и нагрузке дня** — `scripts/summary.py:fat_range(load)` (вес из `config/user.md`; fallback без веса — `config/goals.md`). Тип дня — `day_load()`: **отдых** `1.0–1.2 г/кг` (углей мало, жир даёт сытость и гормоналку), **средний** (≥200 ккал в Z2) `0.9–1.0`, **высокий** (≥300 ккал Z3+/силовая) `0.8–0.9` — освободившийся бюджет в угли вокруг сессии; прогулки и «Прочая активность (Garmin)» нагрузкой не считаются. Утром день = отдых, если пользователь не объявил тренировку; после лога тренировки день переклассифицируется — пересчитать `План` (жиры и угли). В блоке `План` как цель пишется кап дня (`Жиры: 95г`); в высокий день жир смещать в приёмы, удалённые от тренировки (напомнить в чате), еда до/во время — угли с минимумом жира и клетчатки.
4. Правила чтения чисел из `config/goals.md`:
   - `~2400 ккал` -> `2400`;
   - `50-70г/день` -> среднее `60`.
4a. Целевое окно дефицита — по типу дня (см. «Режим и тип дня»); в строке `Можно съесть до …` использовать **нижнюю границу окна** (отдых `до −300`, средний `до 0`, высокий `до +150`).
5. `Базовый расход` = 4-недельное среднее «расхода в покое» из Garmin API — `python3 scripts/garmin_sync.py base` (поле `bmrKilocalories`), хранится константой в `config/user.md`. Это RMR без NEAT, поэтому залогированные тренировки добавляются сверху как и раньше (двойного счёта нет); NEAT-остаток добивается строкой «Прочая активность (Garmin)» при закрытии дня (см. «Синхронизация с Garmin»). Новый вес сам по себе **не** пересчитывает базу формулой — он повод перезапустить `garmin_sync.py base` и обновить константу, если среднее заметно сдвинулось. Вес по-прежнему нужен для белок-флора (г/кг). Поверх сырой константы применяется ручная `Поправка базового расхода` из `config/user.md` (см. п.2) — сырое число сверяется с `garmin_sync.py base`, поправка живёт отдельно и в План уходит их сумма. Если Garmin недоступен — fallback по Миффлину-Сан Жеору:
   - мужчина: `10*вес + 6.25*рост - 5*возраст + 5`;
   - женщина: `10*вес + 6.25*рост - 5*возраст - 161`.

Все числа в дневнике (таблица, `Потреблено`, блок `План`) округлять до целых — никаких дробей. Округляются и ячейки таблицы, и суммы, чтобы `scripts/validate_diary.py` (ε=0.15) сходился без расхождений.

Блок `План` компактный: строка `Базовый расход … Дефицит` несёт все 4 поля (её парсит `scripts/summary.py`), одна строка `Можно съесть до −<нижняя_граница_окна>` (значение `база + потрачено − нижняя_граница_окна − съедено`), макросы — одной строкой. Метки `Углеводы: Nг … осталось: N` и `Белок: …(съедено: N` обязаны сохраняться (их парсят `scripts/summary.py`/`scripts/plan_ration.py`). **Режим в План не писать** — он живёт в заголовке файла H1 `# DD-MM-YYYY-Wnn (диапазон) | Режим: <режим>` (дата дня — в начале `DD-MM-YYYY`, ISO-неделя приклеена `-Wnn`), оттуда же его читает `scripts/plan_ration.py` (метка `Режим:` в хвосте обязана сохраняться; в старых дневниках была `Фаза цикла:` — parse_plan понимает обе).

Формат плана в дневнике (**день отдыха**, режим похудение):
```
## План

- Базовый расход: 2400 ккал | Съедено: 0 | Потрачено: 0 | Дефицит: 2400 ккал
- Можно съесть до −300: 2100 ккал
- Углеводы: 160г (съедено: 0, осталось: 160) · Белок: 143г (съедено: 0) · Жиры: 95г (съедено: 0)

| Время | Продукт/Активность | К | Б | Ж | У | Клетчатка |
|-------|--------------------|---|---|---|---|-----------|

**Потреблено:** К0 | Б0 | Ж0 | У0 | Клет0
```

На **средний день** нижняя граница окна 0 → `Можно съесть до 0`, на **высокий** — −150 → `Можно съесть до +150`; цели углей/жиров пересчитываются по типу дня (угли больше, жир ниже). В режиме **поддержание** любой день — `Можно съесть до 0`.

При создании нового дня шапку + тренд (без остатка групп) брать из `python3 scripts/summary.py weektrend <дата> --no-groups` — вывод = H1 `# DD-MM-YYYY-Wnn (диапазон) | Режим: …` (заголовок файла) + буллеты тренда сразу под ним; вставлять **в начало файла**, `## План` идёт ниже. В чат дублировать полный вывод `python3 scripts/summary.py weektrend <дата>` (с остатком групп) (см. «Недельная накопительная метрика»).

Рацион на день (`ration.md`) при создании нового дня **не генерировать** — только по явному запросу пользователя (команда `рацион`, см. «Рекомендуемый рацион»).

После каждой записи обновлять:
- `съедено` — сумма калорий всех продуктов;
- `потрачено` — сумма `effective_kcal` всех тренировок;
- `дефицит` = `базовый_расход + потрачено - съедено`;
- тип дня (тренировка могла сменить его — тогда пересчитать окно дефицита, цели углей и жиров);
- `можно съесть до −<цель>` = `базовый_расход + потрачено - нижняя_граница_окна - съедено`.

После любого изменения:
- пересчитывать весь блок `План` и строку `Потреблено` заново по содержимому таблицы;
- не вставлять пустые строки внутри markdown-таблицы;
- держать строки таблицы в хронологическом порядке;
- запускать `python3 scripts/format_tables.py diaries/YYYY/MM/DD.md` для выравнивания столбцов.
- запускать `python3 scripts/validate_diary.py diaries/YYYY/MM/DD.md` для проверки согласованности сумм таблицы с блоком `## План` и строкой `**Потреблено:**`; если есть расхождения — показать пользователю и исправить.
- запускать `python3 scripts/plan_ration.py diaries/YYYY/MM/DD.md` и под статус-блоком показывать остаток бюджета + добор из staples в чат (см. «Рекомендуемый рацион» → «Авто-добор после каждой записи»).
- строка `**Потреблено:**` суммирует только еду (К > 0); тренировки (К < 0) в неё не входят — они учитываются только в полях `Потрачено` и `Можно съесть` блока `## План`.
- если меняются правила расчёта или формулировки, то без отдельного явного указания не переписывать прошлые дневники; обновлять только текущий дневник за сегодня.

### Тренировки

Для каждой тренировки определять:
- `raw_kcal` — калории, которые указал пользователь;
- `effective_kcal` — калории после поправочных коэффициентов;
- зону (Z1–Z5 / силовая) — в названии строки дневника **обязательно** указывать зону или тип (`Бег Z2 52 мин`, `Силовая 40 мин`): по ней `scripts/summary.py:day_load()` классифицирует день.

После каждой тренировки:
1. Найти тип тренировки в `config/training_types.md`.
2. Если для типа есть поправочный коэффициент — применить его к `raw_kcal` и получить `effective_kcal`.
3. Добавить строку в таблицу: время, название активности с зоной, `-effective_kcal`.
4. Обновить план:
   - `потрачено += effective_kcal`;
   - `дефицит = базовый + потрачено - съедено`;
   - пересчитать тип дня (`day_load`): если сменился — новое окно дефицита, цели углей и жиров (см. «План на день»);
   - `можно съесть до −<цель>` и цель углей пересчитать по формулам (тренировка входит в них через `Σ effective_kcal`).

Особые правила:
- **%-компенсация углей отменена** (2026-07-04, STRATEGY.md §7a): тренировка попадает в угли через формулу цели дня, а не отдельной прибавкой; колонка компенсации в `config/training_types.md` больше не используется;
- если зона не названа и её нельзя надёжно определить — считать тренировку Z2 (средний день) и спросить зону; для тренировок с часов зону определяет синк по пульсу (см. «Синхронизация с Garmin»), спрашивать не нужно;
- для `спинбайк` / `spinbike` коэффициент не применяется (показания спинбайка считаются эффективными как есть);
- в описании можно показывать исходные и эффективные калории, но в расчётах использовать только `effective_kcal`;
- калории тренировок в таблице всегда записывать отрицательным числом.

Пример: тренировка Z2 на 700 ккал в день отдыха
- `effective_kcal = 700`, строка `| 19:00 | Вело Z2 60 мин | -700 | … |`;
- день переклассифицируется отдых → средний: окно дефицита 300–500 → 0–150, жир 1.0–1.2 → 0.9–1.0 г/кг;
- `Можно съесть до 0 = база + 700 − 0 − съедено`; цель углей выросла на `(700 + Δдефицита + Δжира·9) / 4`.

### Синхронизация с Garmin

Часы (Forerunner 970) — источник расхода калорий. Скрипт `scripts/garmin_sync.py`
(без сторонних зависимостей, токены в `~/.config/diet-log/garmin_tokens.json`, пароль не хранится):

- `python3 scripts/garmin_sync.py fetch [дата]` — сводка дня: `total` (весь расход), `active` (актив + NEAT), `bmr` (покой), шаги;
- `python3 scripts/garmin_sync.py activities [дата]` — тренировки дня: время, тип, длительность, ккал, средний пульс;
- `python3 scripts/garmin_sync.py base [дата]` — 4-нед среднее покоя для `Базового расхода` (запускать при каждом закрытии дня и на взвешивании; константу в `config/user.md` обновлять, если расхождение >2%);
- `python3 scripts/garmin_sync.py weight [дата]` — последнее взвешивание не позже даты: кг, дата взвешивания, источник;
- `--json` — сырой ответ API. Ошибка токена → попросить пользователя выполнить `login` в своём терминале (интерактивный).

**Тренировки с часов** (по команде `синк гармин` или при закрытии дня):
1. `activities <дата>` → каждую тренировку, которой ещё нет в таблице дневника, залогировать: время старта, понятное название + длительность, `-ккал` из вывода скрипта (это **активные** калории: `calories − bmrCalories`, базовый обмен за время тренировки уже сидит в `Базовом расходе`; показания = effective, коэффициенты не применять).
2. В название строки включить зону/тип для `day_load()`: `walking` → Прогулка (нагрузкой не считается), `strength_training` → Силовая (высокий день, зону в название не писать); кардио — зону берёт **из вывода скрипта**: он раскидывает активные ккал по пульсовым зонам пропорционально времени (`Z2 (Z1 13 · Z2 201 · Z3 86 kcal)`) и показывает доминирующую — она идёт в название («Бег Z2 52 мин»), зону у пользователя больше не спрашивать. Если внутри одной тренировки и низкая (Z1–Z2), и высокая (Z3+) части несут **по ≥150 ккал** — логировать двумя строками с их зонами и ккал («Бег Z2 (часть) −210», «Бег Z4 (часть) −180»), чтобы тип дня посчитался честно.
3. Не-тренировки (короткие записи типа `other`: контрастный душ и т.п.) не логировать — их калории доберёт докрутка при закрытии дня.
4. После синка пересчитать тип дня и блок `План` (окно дефицита/угли/жиры могли смениться).

**Докрутка «Потрачено» до часов.** Строка-остаток: `| 23:59 | Прочая активность (Garmin) | -<active − Σ тренировок таблицы> | - | - | - | - |` (NEAT: шаги/быт; компенсация углеводов не применяется; разница ≤ 0 — строку не писать). `active` растёт до полуночи, поэтому:
- **«синк гармин» и «итоги дня» днём/вечером** (день D ещё идёт): `fetch D` → вписать строку по текущему `active` — предварительное число; строка уже есть — обновить, если разошлось больше чем на 20 ккал. Так остаток бюджета в течение дня честнее (NEAT не ждёт закрытия дня); цель углей при этом плавно растёт с активом — это норма.
- **«новый день» утром** (D уже закрыт, число финальное): `fetch D` → если строки нет — добавить; если есть и расходится с финалом больше чем на 20 ккал — поправить. Заодно так же сверить два предыдущих дня (их могли закрыть на компе без токенов) — это единственная разрешённая правка прошлых дневников без явной команды.
  - **Исключение — ручной фикс:** если в названии строки «Прочая активность (Garmin…)» есть пометка `ручной фикс` / `не синкать`, строку НЕ трогать при сверке, даже если Garmin-финал расходится (Garmin-число там заведомо мусорное — напр. фантом-активность от часов на зарядке).
- После любой правки: пересчитать `## План`, прогнать `format_tables.py` и `validate_diary.py`; если правился уже закоммиченный день — закоммитить.

**Вес с Garmin.** При `синк гармин` и при «новом дне» запускать `python3 scripts/garmin_sync.py weight`: если дата взвешивания новее последней записи в истории весов `config/user.md` **и вес отличается от последней записи** — обработать как команду «вес N» (добавить строку в историю с датой взвешивания, дальше обычный флоу веса: `base`, `План`). Дата не новее **или вес тот же** — ничего не делать (дубли одинакового веса в историю не писать), вопросов не задавать.

**Нет файла токенов** (`~/.config/diet-log/garmin_tokens.json`) — комп без Garmin: все Garmin-шаги молча пропускать, еду логировать как обычно, ничего не спрашивать и не напоминать. Докрутка и тренировки догонятся на машине с токенами при следующем «новом дне».

### Таблетки и БАДы

`config/medications.md` хранит таблицу: `Препарат | Доза | Период | Примечание`.

Форматы поля `Период`:
- `бессрочно` — каждый день;
- `2026-04-01..2026-06-30` — курс с датой начала и конца включительно;
- `2026-04-01..бессрочно` — начиная с даты, без конца;
- `пн,ср,пт` — только в указанные дни недели.

Поле `Примечание`:
- `через день` — принимать через день, начиная с даты начала периода. День попадает в приём, если количество дней от даты начала чётное (0, 2, 4…).

Дневной чеклист таблеток живёт в **отдельном файле `pills.md`** в корне, **в `.gitignore`** — локальный, не коммитится, в дневник `diaries/YYYY/MM/DD.md` НЕ вставляется. Файл один на проект, при создании нового дня перезаписывается под текущий день; первая строка — заголовок `# Таблетки YYYY-MM-DD`. Каталог-источник остаётся `config/medications.md` (трекается в git). Если на дату приёма ничего не попадает — `pills.md` не создавать (или оставить пустым).

**При создании нового дневника:**
1. Прочитать `config/medications.md`.
2. Для каждой строки проверить, попадает ли дата дневника в период приёма.
3. Если есть хотя бы одно совпадение — перезаписать `pills.md` чеклистом на текущий день (заголовок + таблица). Совпадений нет — файл не создавать.

Формат файла `pills.md`:
```
# Таблетки 2026-06-28

| · | Препарат | Доза | Приём | Принято |
|---|----------|------|-------|---------|
| 🔲 | Витамин D3 | 2000 МЕ | утро | |
| ✅ | Омега-3 | 1000 мг | вечер | 21:00 |
```

Колонка `·` — статус: `✅` если колонка `Принято` заполнена, `🔲` если пустая.
Колонка `Приём` — плановое время из `config/medications.md` (утро/вечер/обед или конкретное время).
Колонка `Принято` — заполняется фактическим временем приёма (ЧЧ:ММ) или `✓` если время не важно.
При обновлении `Принято` — одновременно менять `·` на `✅`. Ровнять столбцы — `python3 scripts/format_tables.py pills.md`.

**Трекинг приёма:** когда пользователь сообщает о принятых таблетках (например, «утренние таблетки», «принял омегу», «вечерние») — править `pills.md`:
- определить какие строки затронуты (по времени приёма или названию);
- проставить в колонку `Принято` текущее время (вызвать `date +%H:%M`);
- если пользователь не уточнил какие именно — отметить все строки текущего планового времени (утро/вечер).

**Добавление/изменение препарата:**
- Новый препарат добавлять в `config/medications.md` и при необходимости дописывать в чеклист `pills.md` текущего дня.
- Если курс закончился — обновить период в `config/medications.md`.

## Рекомендуемый рацион

Прогнозирует суточный рацион из частых продуктов, чтобы заранее попадать в окно дефицита дня, а не доедать вслепую и не вскрывать перебор постфактум. Частотность — `data/profile.json` (строит `scripts/profile.py` по всем дневникам), подбор — `scripts/plan_ration.py`.

Скрипты:
- `python3 scripts/profile.py` — пересобрать `data/profile.json` (частота, медианная порция, per-gram КБЖУ; `staple` = продукт встречается ≥5 дней). Запускать редко: при заметном изменении рациона или по команде `пересобрать профиль`.
- `python3 scripts/plan_ration.py diaries/YYYY/MM/DD.md` — по блоку `## План` берёт остаток бюджета (ккал по окну дня, добор белка/углей/жира) и предлагает добор из staples дискретными порциями. Пустой дневник → план на весь день; частично съеденный → добор остатка.

Приоритет добора: отстающие floor-группы (окно 7 дней) → белок-флор (постными источниками, протеиновый напиток — полноправный кандидат, максимум один) → углеводы до цели дня (на поддержании) → жир до нижней границы диапазона дня (good-жиром: рыба/орехи/оливковое). Жир живёт в диапазоне типа дня (`scripts/summary.py:fat_range(load)`: отдых 1.0–1.2, средний 0.9–1.0, высокий 0.8–0.9 г/кг; тип определяется по тренировкам дневника, `--load low|mid|high` объявляет запланированную нагрузку заранее): кап дня жёсткий во всех слоях — блюдо, не влезающее в остаток жира, не предлагается; флор добивается последним слоем в рамках остатка ккал, bad-жир флор не закрывает. Если белок-флор не влезает в бюджет ккал, скрипт это показывает — это норма, белок важнее точного дефицита. Порции дискретные (медианные из истории): одно блюдо = одна порция, не масштабируется и не дублируется; блюда, съеденные один раз за всю историю, и блюда крупнее 35% базового расхода в авто-план не попадают.

### Отдельный файл `ration.md`

Рацион живёт в **отдельном файле `ration.md`** в корне проекта, **в `.gitignore`** — локальный, не коммитится, в дневник `diaries/YYYY/MM/DD.md` НЕ вставляется. Файл один на проект; первая строка — заголовок `# Рекомендуемый рацион YYYY-MM-DD` (дата = чьё это рацион, чтобы не спутать со вчерашним). Если файла нет — рацион просто не ведётся, это не ошибка (нормальное состояние: план дня существует, только когда пользователь его попросил).

**Генерация — только по запросу** (2026-08-02). Ни новый день, ни `setup.sh` файл не создают; команда `рацион` — единственный вход: `python3 scripts/plan_ration.py <дневник> --write --force` пишет `ration.md` в чеклист-формате под остаток бюджета на момент запроса. Без `--force` файл пишется, только если его нет или его дата ≠ дате дня (живой файл с галочками не затирается). **Про остатки со вчера не спрашивать** — ручной инвентарь холодильника выведен из употребления 2026-08-02: только усложнял, ничего не давал.

**Гарантированные продукты — `--pin`/`--exclude`, не руками.** Когда пользователь называет продукты, которые точно должны попасть в план (остатки со вчера, «сегодня хочу X», замена одного блюда на другое) — это **аргументы скрипта**, а не повод писать `ration.md` вручную: агент не считает КБЖУ и не подбирает блюда сам, только собирает команду.
- `--pin "Название"` — гарантированный продукт, порция по умолчанию из каталога.
- `--pin "Название:граммы"` — гарантированный продукт на заданный вес (скрипт сам масштабирует КБЖУ от каталожной порции).
- `--exclude "Название"` — никогда не подставлять этот продукт автодобором (замена/наскучило/кончилось).
- Повторяемые флаги, можно комбинировать сколько угодно. Название матчится по каталогу (`product.name`/`alias`), как и везде — точное совпадение, иначе подстрока; неоднозначность или отсутствие — скрипт сам упадёт с понятной ошибкой, не гадать руками.

Пины коммитятся первыми (расходуют бюджет ккал/группы/белок), дальше тот же алгоритм (floor-groups → белок-флор → угли тренировочного дня → жир до флора) добирает остаток вокруг них. Пример:
```
python3 scripts/plan_ration.py diaries/YYYY/MM/DD.md \
  --pin "Паста Барилла:150" --pin "Стейк из форели" \
  --exclude "Стейк тунца" --write --force
```
Пины/исключения ставятся **только по инициативе пользователя** («сегодня хочу X», «X кончился») — сам агент их не выспрашивает. Генерация файла и вся арифметика идут через `--pin`/`--exclude` + `--write`, агент не пишет числа в `ration.md` руками.

Формат — **две таблицы**, каждая со своей строкой `ИТОГО`: сверху `## Осталось` (предложенное, но ещё не съеденное, `🔲`), ниже `## Съедено` (принятые блюда, `✅`). Колонка **`Блюдо`**, НЕ `Продукт`:

```
# Рекомендуемый рацион 2026-06-28

## Осталось

| ·   | Блюдо                    | К       | Б      | Ж     | У     | Съедено |
| --- | ------------------------ | ------- | ------ | ----- | ----- | ------- |
| 🔲  | Экспонента 250г          | 150     | 30     | 0     | 6     |         |
| 🔲  | Сывороточный протеин 30г | 120     | 24     | 2     | 2     |         |
| —   | **ИТОГО**                | **270** | **54** | **2** | **8** |         |

## Съедено

| ·   | Блюдо                    | К      | Б     | Ж     | У      | Съедено |
| --- | ------------------------ | ------ | ----- | ----- | ------ | ------- |
| ✅  | Банан 100г               | 89     | 1     | 0     | 23     | 11:20   |
| —   | **ИТОГО**                | **89** | **1** | **0** | **23** |         |
```

Строки `ИТОГО` — по одной на таблицу, каждая суммирует только блюда своей таблицы; пересчитываются автоматически при каждой раскладке (`scripts/sort_ration.py`). `·` для них всегда `—` — из чек-логики исключены, скрипт держит их последними строками таблиц. Свежий план — весь в `## Осталось`, таблица `## Съедено` пустая (только заголовок и нулевое ИТОГО).

Если `ration.md` правится руками (пользователь назвал блюда явно) — не считать Б по строкам вручную: запускать `python3 scripts/ration_totals.py ration.md diaries/YYYY/MM/DD.md --write`, он пересчитывает строки `ИТОГО` обеих таблиц и печатает сверку с белком-флором (`✓`/`⚠`; белок дня = съедено по дневнику + таблица «Осталось»). Не хватает — добавить ещё белковых блюд и прогнать скрипт заново.

- `·` — `✅` если съедено (колонка `Съедено` заполнена), иначе `🔲`.
- Таблица `## Осталось` = что осталось съесть по плану (живой остаток), её `ИТОГО` — остаток КБЖУ плана; `## Съедено` — принятая часть плана со своим `ИТОГО`.
- Файл справочный: в `**Потреблено:**` и суммы блока `## План` НЕ входит. Дневниковые скрипты (`scripts/validate_diary.py`/`scripts/summary.py`) его вообще не видят (он не часть дневника); ровнять столбцы — `python3 scripts/format_tables.py ration.md`.

### Чек = лог

Когда пользователь сообщает что съел плановое блюдо («съел боул», «банан из плана»):
1. вызвать `date +%H:%M`;
2. в строке `ration.md` проставить `Съедено` = время, `·` → `✅`;
3. **и добавить реальную строку в таблицу питания дневника** (время, блюдо, КБЖУ) — таблица питания остаётся единственным источником `Потреблено`;
4. после любой пометки в `ration.md` переразложить таблицы — `python3 scripts/sort_ration.py ration.md && python3 scripts/format_tables.py ration.md` (✅-строка переезжает в таблицу «Съедено», 🔲 остаются в «Осталось», оба `ИТОГО` пересчитываются; порядок внутри таблиц цел).

Так план и факт не расходятся, двойного счёта нет. Съел вне плана → логировать как обычно в таблицу питания, в `ration.md` не вносить. Если `ration.md` нет — шаги 2 и 4 пропустить.

### Авто-добор после каждой записи

После пересчёта блока `## План` запускать `python3 scripts/plan_ration.py diaries/YYYY/MM/DD.md` и под статус-блоком показывать остаток + добор в чат (эфемерно, в дневник не писать). Если `ration.md` существует и пользователь заметно отклонился (переел/недоел) — пере-резать невычеркнутые строки под новый остаток, дискретными порциями, не дампить одним блюдом. Файла нет — ничего не создавать, добор живёт только в чате.

## Неопределённости

- Если продукт, порция, тип тренировки или найденные значения неоднозначны — задать уточняющий вопрос. Не гадать.
- Если пользователь не указал граммовку/КБЖУ, не задавать уточняющие вопросы "на всякий случай" и не просить этикетку: сначала использовать порцию по умолчанию из каталога или самостоятельно найти данные в интернете и зафиксировать (при необходимости помечать как оценку). Уточнять только если данных нет совсем или есть несколько равновероятных вариантов.
- Если продукт найден в интернете, но источники сильно расходятся — показать варианты и запросить подтверждение.
- Если дедлайн в `config/goals.md` уже в прошлом — сообщить об этом пользователю, но продолжить расчёты по текущим числам.

2. Если нет — выполнить `git init`.
3. Добавить все изменённые файлы: `git add .`.
4. Если есть staged changes — сделать коммит: `git commit -m "день YYYY-MM-DD"`.

## Недельная накопительная метрика

На старте каждого дня (при создании дневника или по команде `недельный прогресс`) считать накопительный итог текущей ISO-недели по уже имеющимся записям — `python3 scripts/summary.py weektrend <дата>`.

Скрипт берёт записи недели **до** указанной даты (сам день ещё пуст) для тренда дефицита/белка (ISO-неделя), переиспользует агрегатор `summarize()` и выдаёт готовый markdown-блок. Цель дефицита — **микс окон** прошедших дней недели (окно каждого дня по его типу, §7a). Остаток групп считается **скользящим окном 7 дней** (`ref−6..ref`, включая сам день) — понедельник не обнуляет потолки и долги групп; ISO-рамка остаётся только рамкой отчёта:

```
# 15-06-2026-W25 (2026-06-15..2026-06-21) | Режим: похудение

- Средний суточный дефицит: 220 ккал (цель по миксу дней 150–320) ✓
- Белок: 145г/день (цель 143) ⚠ недобор 25г/день
- Прогноз недельного дефицита при тренде: 1540 ккал (окно 1050–2240) ✓

### Остаток групп (7 дней 2026-06-09..2026-06-15) — добрать
- рыба:         ⚠ 2.5/3 — добрать 0.5
- овощи:        ✗ 1.0/14 — добрать 13.0
…
### Остаток групп — потолки
- сладкое:      ✗ 4.4/2 — перебор 2.4

### Качество жира (7 дней 2026-06-09..2026-06-15)
- bad: ⚠ 17% (потолок 15) — фритюр/выпечка/переработка
- good 28% — можно больше (ориентир 40+): рыба, орехи, оливковое
```

H1 `# DD-MM-YYYY-Wnn (диапазон) | Режим: <режим>` — заголовок файла (заменяет `# YYYY-MM-DD` и бывший `## Недельный прогресс (на …)`, слиты в одну строку: дата+неделя+статус). Единственное место режима/недели; метка `Режим:` в хвосте обязана сохраняться — её парсит `scripts/plan_ration.py` (в старых дневниках `Фаза цикла:` — понимает обе). Буллеты тренда идут прямо под H1. Строки `Дней осталось`/`Дней с записями` дропнуты. Строка `Белок` показывается **только при недоборе** (avg < флор); если средний белок цель закрывает — строки нет. Строка `Жиры` — только если среднее за неделю вне полного диапазона `0.8–1.2 г/кг`. Блок «Качество жира» (окно 7 дней, доли по граммам): `bad ≤ 15%` — сигнал (✓/⚠/✗), `good ≥ 40%` — подсказка без символа, показывается только при недоборе; обе планки в норме — одна строка `- bad: ✓ 12% · good 43%`.

- В чат (полный вывод `weektrend`) добавляется остаток по группам (floor = добрать, limit = потолки) — это бывший `medweek`, теперь часть `weektrend`. Непривязанные к каталогу блюда перечисляются в конце (дыры каталога). **В дневник остаток групп НЕ писать** — он застывает за день; живой остаток всегда через `scripts/summary.py weektrend`.
- В понедельник (или если записей недели ещё нет) тренд сообщает «Первый день недели, тренда пока нет», но остаток групп всё равно считается (в чате).
- В режиме поддержания дефицитные строки формулируются как удержание (цель ~0); в режиме похудения цель тренда — «микс окон дней» (сумма окон дефицита по типам прошедших дней недели).
- Блок — маркированный список, поэтому `scripts/format_tables.py` его не трогает, а `scripts/validate_diary.py` не ломается.
- При создании нового дня в дневник вставлять **в начало файла** H1-шапку + тренд (`python3 scripts/summary.py weektrend <дата> --no-groups`); `## План` идёт ниже. В чат дублировать **полный** вывод (`weektrend <дата>` без флага — с остатком групп).

## Формат каталога (`data/diet.db`)

Каталог живёт в SQLite `data/diet.db` (схема — `docs/STRATEGY.md` §11). Основное:

- `product(name, portion_raw, portion_g, k, b, zh, u, fiber, prep_effort, estimated, review, fat_quality)` — `name` каноническое и уникальное; `portion_g` = граммы порции (null для шт/мл/«порция»); `review=1` — продукт ждёт разметки по группам; `fat_quality ∈ {good,neutral,bad}` (дефолт `neutral`) — качество жира продукта (рубрика docs/STRATEGY.md §7), ставится через `scripts/db add --fat-quality good|bad` для жирных продуктов выше порога (жир ≥30% ккал или ≥5г/порцию).
- `alias(product_id, text)` — альтернативные написания (одна строка на алиас).
- `food_group` / `product_group(weight)` — группы продуктов (квоты лёгкого средиземноморского уклона) и веса (в т.ч. композиты).

Добавление/поиск — только через `scripts/db add` / `scripts/db find` (см. баннер вверху).

## Итоги недели и месяца

- `итоги недели` считать по ISO-неделе: понедельник-воскресенье.
- `итоги месяца` считать по календарному месяцу.
- Для периода собирать все файлы дневников, которые попадают в диапазон дат.
- Для `итоги недели` без уточнения брать неделю, в которую входит текущая дата.
- Для `итоги месяца` без уточнения брать месяц, в который входит текущая дата.
- Если пользователь явно указал период, использовать его: например `итоги недели за 2026-03-09` или `итоги месяца за 2026-02`.
- Не считать пропущенные дни как нули.
- Если файла за день нет — считать день пропущенным.
- Если файл есть, но в таблице нет записей — считать день без данных.
- Если в дне есть только еда или только тренировка — считать день частично заполненным.
- День считать `днём с записью`, если в таблице дневника есть хотя бы одна строка продукта или активности.
- Все агрегаты считать по фактически найденным данным дневников, а не по предположениям.

### Алгоритм расчёта

**ВАЖНО:** Вместо ручного парсинга дневников использовать скрипт `scripts/summary.py`:

```bash
python3 scripts/summary.py week              # текущая неделя
python3 scripts/summary.py week 2026-04-14   # неделя с датой внутри
python3 scripts/summary.py month             # текущий месяц
python3 scripts/summary.py month 2026-04-01  # конкретный месяц
python3 scripts/summary.py weektrend         # накопительная метрика текущей недели
python3 scripts/summary.py 2026-04-01..2026-04-30  # произвольный диапазон
```

Скрипт читает `**Итого:**` из каждого дневника и строку `Базовый расход ... Съедено ... Потрачено ... Дефицит` из `## План`, вес берёт из `config/user.md`. Вывод в формате итогов — готов для показа пользователю.

Вручную парсить только если скрипт недоступен или нужны данные, которых в нём нет.

1. Определить границы периода.
2. Найти все дневники `diaries/YYYY/MM/DD.md`, попадающие в этот диапазон.
3. Для каждого дня:
   - если файла нет — пометить день как пропущенный;
   - если файл есть, но строк таблицы нет — пометить как день без данных;
   - если строки есть — извлечь итоговые значения `К`, `Б`, `Ж`, `У`, `Клет`, а также `Съедено`, `Потрачено`, `Дефицит`.
4. Сложить суммарные значения по дням с данными.
5. Посчитать средние значения только по дням с записями.
6. Найти все записи веса из `config/user.md`, попадающие в период.
7. Если внутри периода есть минимум две записи веса — показать изменение веса от первой к последней.

В итогах периода показывать:
- период;
- количество дней в периоде;
- количество дней с записями;
- количество дней без данных;
- покрытие в процентах;
- статус полноты: `полный`, `частичный` или `недостаточно данных`;
- суммарно: съедено, потрачено тренировками, дефицит;
- средние значения на день с записью: калории, дефицит, белки, жиры, углеводы;
- список пропущенных дней;
- список дней без данных;
- при наличии данных веса в `config/user.md` внутри периода — изменение веса от первой записи периода к последней.

Формат ответа:

```md
## Итоги недели 2026-03-09..2026-03-15

- Покрытие: 6/7 дней (85.7%) | Статус: частичный
- Дней без данных: 1
- Съедено: 11400 ккал
- Потрачено тренировками: 2300 ккал
- Суммарный дефицит: 5300 ккал
- Среднее съедено на день с записью: 1900 ккал
- Средний дефицит на день с записью: 883 ккал
- Белок: 910г всего | 152г/день с записью
- Жиры: 390г всего | 65г/день с записью
- Углеводы: 1680г всего | 280г/день с записью
- Пропущенные дни: 2026-03-15
- Дни без данных: нет
- Вес: 86.3 -> 85.8 кг (-0.5 кг)
```

Правила полноты:
- `полный` — все дни периода имеют записи;
- `частичный` — покрытие от `80%` включительно;
- `недостаточно данных` — покрытие ниже `80%`.

Сравнение с целями:
- сравнивать фактический дефицит только с целевым дефицитом за дни, где есть записи;
- не делать вывод `цель выполнена` или `цель не выполнена`, если статус периода `недостаточно данных`.

Corner cases:
- если в периоде нет ни одного дня с записью — вывести только факт отсутствия данных и список пропущенных дней;
- если покрытие ниже `80%` — не делать интерпретацию тренда по питанию;
- если внутри периода только одна запись веса — показать её как факт, но не считать изменение;
- если период пересекает текущий незавершённый день, всё равно считать его как обычный день по имеющимся на момент запроса данным;
- если итоговые строки дневников расходятся с суммой таблицы, ориентироваться на таблицу и пересчитывать значения заново.

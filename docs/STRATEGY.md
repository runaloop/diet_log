# Стратегия: средиземноморский недельный планнер

> Статус: согласованный стратегический спек. Реализация — отдельными фазами (§14).
> Код по этому документу ещё не написан; текущий `scripts/plan_ration.py` — старый
> суточный макро-филлер, подлежит замене (§14, фаза 4).

## 1. Суть сдвига

Текущий планнер — **макро-филлер снизу вверх**: берёт частые продукты из
истории, затыкает дыры в суточном КБЖУ. Эвристики (демоушен порошков,
орехи-в-жиры) — пластыри, чтобы результат был съедобным.

Новая логика — **сверху вниз, средиземноморский коуч**:
- цель = средиземноморский паттерн питания;
- КБЖУ/дефицит = **ограничители**, не целевая функция;
- история (`data/profile.json`/каталог) = **склад конкретных блюд и порций**, которыми
  паттерн реализуется, а не драйвер выбора.

## 2. Горизонт оптимизации = неделя

Сутки — **свободная переменная**, которая капает в недельный итог. Ни один день
не обязан закрыть всё.

Недельная рамка двойная (решение 2026-07-02):
- **Группы и анти-повтор — скользящее окно 7 дней**, заканчивающееся сегодня.
  Календарный понедельник не амнистирует перебор потолков (чипсы в воскресенье
  окно помнит до следующего воскресенья) и не сжигает долг полов (провал по
  овощам не прощается сменой ISO-номера недели).
- **Дефицит — по дням** (§7a, с 2026-07-04): окно дефицита задаёт нагрузка
  конкретного дня, недельного цикла 2+1 больше нет; ISO-неделя осталась
  только рамкой отчётов (weektrend / итоги недели).

Планнер **гасит остаток окна**: смотрит, что за последние 7 дней осталось
добрать (по средиземноморским группам И по дефициту/белку), и предлагает
сегодня то, что закрывает самый отстающий остаток — в рамках сегодняшнего
мягкого потолка ккал.

## 3. Стек приоритетов (лексикографический)

```
1. СРЕДИЗЕМНОМОРСКИЙ ПАТТЕРН   → задаёт СОСТАВ (какие группы еды, в какой пропорции)
2. НЕДЕЛЬНЫЙ СМЫСЛ (цикл)       → задаёт ОГИБАЮЩУЮ недели (дефицит сушит, загрузка грузит угли)
3. СУТОЧНЫЕ ЦЕЛИ + ПОДСТРОЙКА   → задаёт КОЛИЧЕСТВА сегодня (мягкий потолок, пере-прицел в течение дня)
4. РАЗУМНОЕ РАЗНООБРАЗИЕ         → анти-повтор (ротация внутри групп, не дублировать неделю/день)
```

КБЖУ перестаёт быть целевой функцией — становится constraint'ом слоя 3.

## 4. Целевая функция

**Средне-недельный «инкам» средиземноморский.** Конкретно за неделю:
- квоты «пол»-групп выполнены (рыба, бобовые, овощи, фрукты, злаки, орехи, йогурт);
- «потолок»-группы не превышены (красное мясо, сладкое/обработка, добавки);
- средний суточный дефицит недели = цель фазы (`config/cycle.md`/`config/goals.md`);
- белок-флор держится **каждый день** (см. §8).

## 5. Остаток недели — действенная метрика

Не накопленный счёт, а **что осталось добрать**:

```
остаток_группы   = квота_недели − съедено_за_неделю   (для «пол»: добираем; для «потолок»: запас до лимита)
остаток_дефицита = цель_дефицита_недели − накоплено
остаток_белка    = суточный флор − съедено_сегодня     (белок суточный, не копится)
```

Производная величина — **нигде не хранится**, считается из дневников × маппинг
групп, как `scripts/summary.py weektrend`. Поддерживаем только маппинг (§11), не счёт.

Планнер ранжирует группы по **степени отставания остатка** и гасит самые
отстающие первыми.

## 6. Средиземноморская модель: группы + недельные квоты

Стартовая модель (канон Med, под подгонку §15). `kind`:
- **пол** — добираем до квоты;
- **умеренно** — желательно, но не давим;
- **потолок** — не превышаем.

| Группа | kind | Квота/нед | Примечание |
|--------|------|-----------|------------|
| Овощи | пол | ≥2 порц/день | база рациона |
| Фрукты | пол | 1–2/день | |
| Цельные злаки | пол | ежедневно | |
| Бобовые | пол | ≥3 | |
| Рыба/морепродукты | пол | ≥5 ед (§6a) | граммовая (1 ед = 100г) |
| Орехи/семена | пол | горсть/день | |
| Йогурт/сыр | пол | ежедневно умеренно | греческий йогурт — эталон |
| Птица | потолок | ≤4 ед (§6a) | граммовая (1 ед = 100г); держим ≤ рыбы |
| Яйца | умеренно | 2–4 | |
| Оливковое масло | — | — | **дефолтный жир** (§7), не жёсткая квота |
| Красное мясо | потолок | ≤1 | |
| Сладкое/обработка | потолок | ≤2 | десерты, сахар, ультра-обработка, снеки |
| Добавки/порошки | потолок | (мягкий) | протеин/коктейли/гейнер — функционально нужны для белка, но не Med-еда; держим в фоне |

Композитное блюдо вкладывается в **несколько групп** с весами (§11): напр.
корейский суп → `{злак 1.0, яйцо 0.5, овощи 0.5}`. Граммы компонентов не нужны —
только вклад в квоту группы. КБЖУ блюда остаётся тоталом.

### 6a. Граммовые группы: рыба и птица

Событийный счёт («одна запись = вес») перекашивает мясо/рыбу: 25г сублимат-чипсов
весили столько же, сколько 150г стейка. Поэтому **рыба и птица** (set
`GRAM_GROUPS` в `scripts/summary.py`) считаются в граммах:

- **1 единица = 100г мяса/рыбы как съедено.** `servings = граммы_записи × вес / 100`.
- `product_group.weight` для этих групп = **доля мяса в блюде**: чистый кусок 1.0
  (стейк тунца, индейка гриль), суп с курицей ~0.1, сублимат/джерки >1.0
  (концентрат — чипсы Дымов 2.5).
- Квоты в единицах: **рыба ≥5** (≈500г/нед, пол), **птица ≤4** (≈400г/нед, потолок).
  Делим на 7 → ориентир ~71г рыбы / ~57г птицы в день. Правило Med: рыба ≥ птицы.

Прочие 11 групп остаются на событийных флагах — это адаптация двух групп, не
переделка модели. Эталон «100г = 1 ед» и квоты 5/4 — **наше** решение (Med задаёт
частоту порций, не граммы), не дословная Med-рекомендация. Логика добора/потолков
(`plan_ration.py:dish_servings`) граммовая для этих групп, флаговая для остальных.

## 7. Жиры — оливковое как дефолт

Оливковое масло пользователь принимает редко → **не делаем ежедневной жёсткой
квотой**. Делаем **дефолтным жиром**: когда нужен добор жира, планнер тянет
оливковое/оливки/орехи, а не случайный жир. Мягкий нудж, не обязаловка.

### Количество жира — доля бюджета дня (25–42%), циклируется по нагрузке

Ккал-потолок сам по себе жир не ограничивает: жирные блюда вытесняют угли
внутри потолка (фейл 2026-07-02 — план на 97г жира при 122г углей на
загрузочной неделе). А чистый потолок не ловит обратный фейл — день на 20г
жира (гормоны, жирорастворимые витамины). Поэтому жир — **второй суточный
ограничитель** с двумя границами, и границы плавают по нагрузке дня
(жир ходит противофазой к углям).

Границы задаются **долей бюджета дня, а не г/кг** (пересмотр 2026-08-03).
Г/кг привязывает жир к весу, но жмёт его не вес, а бюджет — а бюджет падает
и от снижения веса, и от роста дефицита. Фейл 2026-08-03: вес 80.1 при
дефиците 300–500 дал бюджет дня отдыха 1633 ккал, из которых старый флор
1.0 г/кг съедал 720 (44% дня **до** первого грамма углей) — на угли
оставалось 84г, то есть правило требовало почти кето-дня и расходилось
вдвое с фактической привычкой (медиана 32% ккал из жира за 35 дней).
Доля от бюджета держит профиль постоянным при любом весе и дефиците:
граммы жира выходят почти плоскими (64–87г), а угли ходят 120→340г — то
есть противофазу создаёт не количество жира, а его доля.

- **Тип дня** (`scripts/summary.py:day_load()`, по строкам тренировок
  дневника): **высокий** — ≥300 ккал в Z3+/силовая/интервалы; **средний** —
  ≥200 ккал тренировок с учётом Z2 и тренировок без указанной зоны;
  **отдых** — остальное. Прогулки/ходьба и NEAT-строка «Прочая активность
  (Garmin)» нагрузкой не считаются. Утром день без тренировок = отдых;
  запланированную нагрузку объявляет пользователь (`plan_ration.py --load
  low|mid|high`), иначе день переклассифицируется по факту лога тренировки.
- **Бюджет дня** (`summary.py:day_budget()`) = `базовый расход + Σ effective
  тренировок − нижняя граница окна дефицита дня` — это «сколько можно съесть»
  из блока `## План`, до вычета съеденного. Именно от него берётся доля.
- **Диапазоны** (`summary.py:DAY_FAT_SHARE`, `fat_range(load, budget=…)`):
  - отдых — **35–42% бюджета**: углей мало, жир даёт сытость (на дефиците
    критично) и держит гормоналку; яйца, жирная рыба, орехи, оливковое;
  - средний — **30–35%**;
  - высокий — **25–30%**, план целится в нижнюю границу: весь
    освободившийся бюджет — в угли вокруг сессии; жир смещать в приёмы,
    удалённые от тренировки (peri-workout еда — угли с минимумом жира и
    клетчатки; это рекомендация агента в чате, скрипты тайминг не проверяют).
  - **Страховка снизу** — `FAT_FLOOR_PER_KG = 0.6 г/кг`: флор не опускается
    ниже, каким бы маленьким ни стал бюджет (гормоны, жирорастворимые
    витамины). Вес — последняя запись `config/user.md`; без веса или без
    бюджета `fat_range` откатывается на старую полосу 0.8–1.2 г/кг.
- Для **генерации плана** кап дня жёсткий: блюдо, не влезающее в остаток
  жира, не предлагается; освободившиеся ккал уходят углям. Белок-флор
  добивается постными источниками — протеиновый напиток
  (экспонента/сывороточный, ~0 жира, всегда в наличии) — полноправный
  кандидат топапа, максимум один в день. **Флор дня** — последний слой
  (`plan_ration.py:fat_floor_topup`): если день после всех слоёв ниже
  нижней границы, добрать good-жиром (олива/орехи/рыба — «дефолтный жир»),
  bad-блюда флор не закрывают; слой мягче белкового — потолок ккал не
  пробивает.
- Для **факта дня** обе границы — мягкий сигнал (статус ⚠ при переборе капа
  дня ×1.2 или ниже флора дня), еда не запрещается. **Средние за период**
  судятся по полной полосе 25–42% от **среднего бюджета дня периода**
  (`summary.py:avg_day_budget()`) строго, без ×1.2-буфера — циклирование
  по дням внутри неё и должно ходить.

### Качество жира — тег `fat_quality`

Сумма граммов жира скрывает источник: 14г оливкового ≠ 14г из фритюра по пользе
(эндокринка, омега-6:омега-3). Поэтому у продукта есть `fat_quality ∈
{good, neutral, bad}` (колонка в `product`, дефолт `neutral`).

Тег описывает **доминирующий тип жира в продукте**. Значим, только если жир —
заметная часть: **порог** `жир ≥ 30% калорий` ИЛИ `≥ 5г на порцию`. Ниже порога —
`neutral` по умолчанию, руками не размечаем (вклад в недельный счёт ~0).

Дерево решений для продуктов выше порога:
1. транс / фритюр / маргарин / жарка на дешёвом рафинаде / промышленная выпечка /
   батончики на пальме-гидрогенизате → **bad**;
2. жир в основном из рыбы / оливок / орехов / семян / авокадо → **good**;
3. остальное (молочка, яйца, цельное мясо, смешанные блюда, насыщенный из цельной
   еды, чистый шоколад/какао-масло) → **neutral**.

Дефолты спорного: орехи/семена/оливковое/рыба/авокадо → good; желток/сыр/молочка/
красное мясо → neutral (колбаса/переработка → bad); хумус → neutral; жареные
морепродукты (кляр/фритюр) → НЕ good, перебивает фритюр.

Бутстрап каталога: группы `рыба`/`орехи`/`оливковое` → good, прочее neutral,
дальше руками только очевидные bad (фритюр/выпечка/батончики) и good вне групп.
Новый продукт тегается по этому же дереву при заведении (`scripts/db add --fat-quality`).

Метрика (в `weektrend`, блок «Качество жира», окно 7 дней как у групп): не
штуки, а **граммы жира × качество** — доля жира из good / neutral / bad
(`summary.py:fat_quality_lines`, непривязанные строки считаются neutral —
неизвестное ≠ вредное). Две планки с разной семантикой:

- **bad ≤ 15%** недельного жира — полноценный сигнал (✓ / ⚠ / ✗ при >30%):
  перебор — это проблема;
- **good ≥ 40%** — нудж без символа: строка-рекомендация появляется только
  пока good ниже ориентира и молча исчезает при достижении. Недобор good —
  не проблема, а возможность. Порог стартовый (факт на 2026-07: ~22–37%);
  когда 40 станет стабильной нормой — поднять константу
  (`summary.py:FAT_GOOD_SHARE_TARGET`).

Обе планки в норме → блок сжимается до одной зелёной строки. Планнер тянет
неделю к ориентиру сам: в `fat_floor_topup` кандидаты сортируются good-первыми.
Омега-3 косвенно уже виден через группы `рыба`/`орехи` + добавка Омега-3 в
`config/medications.md`.

## 7a. Дефицит — периодизация по нагрузке дня

Недельный цикл «2 недели дефицита / 1 неделя поддержания» заменён
(2026-07-04) дневной периодизацией: дефицит живёт в лёгкие дни,
тренировочные дни заправляются. Классификация дня — общая с жировым
диапазоном (§7, `summary.py:day_load()`):

| День | Триггер | Окно дефицита | Жир (§7) |
|------|---------|---------------|----------|
| отдых | нет тренировок / Z1 / прогулки | 300–500 (из `config/goals.md`) | 35–42% бюджета |
| средний | ≥200 ккал в Z2 (или зона неизвестна) | 0–150 | 30–35% бюджета |
| высокий | ≥300 ккал в Z3+/силовая/интервалы | ~0 (−150…+150) | 25–30% бюджета |

- **Carryover**: вчера в Z3+ сожжено >900 ккал → сегодня минимум «средний»
  (восстановление), даже если это отдых. Действует на всю классификацию дня —
  и дефицит, и жир (`summary.py:CARRYOVER_KCAL`).
- **Режим** (`config/cycle.md`): `похудение` — таблица выше; `поддержание`
  (цель достигнута или диет-брейк) — все дни ~0 (±150). Диет-брейк = временное
  переключение режима, отдельной механики нет.
- Утром день без тренировок = отдых; запланированную нагрузку объявляет
  пользователь (`plan_ration.py --load`), иначе день переклассифицируется по
  факту лога тренировки. Бюджет дня в течение дня только растёт — безопасно.
- **Цель углей дня**: `(база + Σ effective_kcal тренировок − нижняя_граница_окна
  − белок_флор·4 − жир_флор_дня·9) / 4` — бюджет, освобождённый жиром и
  дефицитом, уходит в угли тренировочного дня. Старая %-компенсация углей от
  тренировок отменена (иначе двойной счёт).
- Отчёты: цель периода = **микс окон его дней** (`summarize()` суммирует окна
  по дням с данными). Статус дня: в окне ✓; ниже окна ⚠/✗ (переедание); выше
  окна на тренировочный день ⚠ (недоедание — добрать углей), на отдых ✓.

Симуляция на факте 2026-06-06..07-03 (11 отдых / 7 средних / 10 высоких,
carryover ×1): целевой дефицит ~1230 ккал/нед ≈ 0.16 кг/нед — темп фактических
недель сохраняется, еда перераспределяется в тренировочные дни.

## 8. Белок-флор — единственное суточное жёсткое

Минимальная суточная планка белка: **1.8 г/кг массы тела** — с 2026-07-04
плоская, без фазового множителя (пробуем на дневной периодизации §7a; станет
трудно держать мышцы — поднять `summary.py:PROTEIN_PER_KG`).

Вес — из `config/user.md` (последняя запись). Формула заменяет фикс `170`
в `config/goals.md`. Всё прочее (группы, разнообразие) — недельное.

## 9. Тренировочный день — добор углей

Задача — заправить тренировочные дни. Планнер добирает carb-forward блюда
(углеводо-доминантные, низкожировые) до **полной** суточной цели по углеводам
в средние/высокие дни (§7a) и во все дни режима поддержания; в день отдыха
режима похудения слой выключен — там живёт дефицит.

> До 2026-07-04 слой включался на загрузочной ISO-неделе цикла 2+1 — цикл
> заменён дневной периодизацией (§7a). Ещё раньше (до 2026-07-01) был
> train/rest-сплит 0.6 таргета — убран по решению пользователя.

## 10. Слой ограничений реализма

- **Не люблю готовить** → байас на no-cook / готовое / сборка. Поле `prep_effort`,
  предпочитаем низкое.
- **Решение нужно в момент голода** → секунды, не подбор: у любого плана есть
  no-cook ветка, есть режим «что съесть сейчас?» (§12). Урок пад-тая
  2026-07-02: пока план требовал варить гречку, обед случился в ресторане.
- **Ресторан без КБЖУ-состава** → планнер терпит блюда с неизвестными/оценочными
  макросами: размечает группы + грубые КБЖУ, не ломается. В недельной рамке один
  мутный ресторанный обед усредняется — не критично. Частые рестораны/доставки —
  источник доступной еды наравне с холодильником (§11 `avail`).
- **Еду менять можно** → не залочены в историю; предлагаем новое средиземноморское,
  но реально покупаемое — через «докупить» в дневном плане (§12).

## 11. Данные: SQLite как единственный канон

Маппинг групп + композиты + prep_effort в markdown = колонки-списки, файл пухнет,
мелкие LLM давятся. Переезжаем на SQLite.

**Единственный источник правды — `data/diet.db`.** Никаких двух синхронизируемых руками
баз, никакого промежуточного текстового зеркала. `products.md` удалён (фаза 0/1);
вся работа с каталогом — через обёртку `db`.

```sql
product(id, name, portion_g, k, b, zh, u, fiber, prep_effort, estimated, review,
        fat_quality, avail)
        -- prep: low|med|high; estimated/review: флаги оценки и недоразметки
        -- fat_quality: good|neutral|bad (дефолт neutral; рубрика §7)
        -- avail: always|stock|resto:<имя>|NULL — доступность (§10, §12):
        --   always = staple, дома всегда; stock = куплено, лежит сейчас;
        --   resto:X = частый ресторан/доставка; NULL = неизвестно.
        --   Композер берёт в план только always/stock/resto; NULL — кандидат
        --   в «докупить». Обновление житейское: «купил X,Y» → stock;
        --   «кончилось X» → NULL; закупочная ревизия раз в неделю, не учёт.
alias(product_id, text)
med_group(id, name, kind, quota_week)        -- kind: пол|умеренно|потолок
product_group(product_id, group_id, weight)  -- m2m, композиты, weight 0..1
```

Остаток недели НЕ хранится — вычисляется SQL-запросом из дневников × `product_group`.

### Жизненный цикл данных

Канон = `data/diet.db`. Сверху — обёртка `db` (ванлайнеры записи и грепа). Git-дифф
бинаря решается textconv'ом, без второго файла.

```bash
db find лосось                    # SELECT ... WHERE name LIKE '%лосось%'
db q "select name,k,b from product where b>20 order by b desc"   # сырой SQL
db add "Лосось" --port 100 --k 208 --b 20 --zh 13 --u 0          # INSERT, схема валидируется
db tag "Корейский суп с лапшой" злак=1.0 яйцо=0.5 овощи=0.5      # композит-теги
db review                         # продукты с флагом review (недоразмеченные)
```

```
# .gitattributes
data/diet.db diff=sqlite3
# git config (один раз)
[diff "sqlite3"]
  textconv = sqlite3 $1 .dump
```

→ `git diff` рендерит `.db` как SQL-дамп, диффы читаемые. `.db` коммитится.

| Событие | Кто | Чем |
|---------|-----|-----|
| Логирую новый продукт | LLM при записи дня | `db add …` → INSERT + авто-классификация группы (флаг `review`) |
| Med-разметка (фаза 1) | ассистент + ревизия пользователя | `db tag …`, дочистка через `db review` |
| Грубое ресторанное блюдо | LLM | `db add … --estimate`, группы вручную/оценкой |
| Планнер / итоги | скрипты | только **читают** `data/diet.db` (остаток недели = SQL-запрос) |
| Греп руками | пользователь | `db find …` или `sqlite3 data/diet.db "…"` |

- Ввод еды для пользователя не меняется: LLM пишет в **дневник** markdown; каталог
  трогают только через `db` (LLM вызывает `db add` вместо правки `products.md`).
- Дневники остаются markdown (логи суточные, человекочитаемые).
- Композит = несколько строк `product_group`: суп → `{злак 1.0, яйцо 0.5, овощи 0.5}`.

## 12. Как рождается дневная рекомендация (композер-коуч)

> Редизайн 2026-07-02. Алгоритмический генератор (жадный набор атомов истории
> по остаткам групп) выдавал формально валидные, но гастрономически абсурдные
> планы (§16) — Гудхарт по метрикам. Авторство плана передано LLM-агенту,
> скрипты понижены до счётчиков/валидаторов.

Роли:
- **Счётчик (скрипты)** — `summary.py` (остаток групп rolling-7, тренд),
  `plan_ration.py` (макро-коробка дня: ккал-потолок, белок-флор, жир-кап,
  угли-цель; черновой добор как подсказка агенту, не как готовый план).
- **Композер (агент)** — собирает день из **приёмов** (обед/ужин/перекусы),
  а не плоского списка: сочетания берёт из реальных пар истории (что юзер
  ел вместе) и Med-шаблонов («рыба + овощи + злак»); только **доступная**
  еда (§11: `avail`), всегда есть **no-cook ветка** (§10); плюс 1–2
  «средиземноморских сдвига» дня и список «докупить».
- **Критик (агент)** — прогоняет план по `docs/CRINGE.md` (§16) + контексту
  (что ел вчера/сегодня, время суток, наличие); правит до чистоты.
- **Валидатор (скрипты)** — арифметика итога против коробки
  (`ration_totals.py`, белок-флор/жир-кап/потолки групп).

Пайплайн дня:
1. Счётчик: режим + тип дня (§7a), вес, макро-коробка (`Б ≥ флор · Ж в
   диапазоне дня · У → цель дня · К ≤ потолок окна`), остаток групп за окно 7 дней.
2. Композер: 2–4 приёма из доступного + no-cook альтернатива + сдвиг недели
   + докупить.
3. Критик: чек по CRINGE.md, правка.
4. Валидатор: числа сходятся с коробкой — выдача; нет — возврат композеру.

Отдельный режим **«что съесть сейчас?»**: юзер голоден в моменте — один
конкретный ответ из наличия за секунды, no-cook первым, без пересборки всего
дня (кейс пад-тая: решение нужно быстрее, чем сварится полкило гречки).

Макросы — ограничители коробки, не целевая функция. Миграция к Med-паттерну
идёт через ежедневные «сдвиги» (замена одного не-Med блюда на Med-аналог,
докупка), а не через мгновенно-идеальный список.

## 16. Кринж-контур: качество плана как еды

**Кринж** = план, проходящий все числовые проверки (КБЖУ, группы, квоты), но
непригодный как еда реального человека. Метриками не ловится по построению
(Гудхарт) — ловится LLM-критиком со здравым смыслом + корпусом прецедентов.

- Корпус — **`docs/CRINGE.md`**: живой чеклист анти-паттернов с примерами из
  реального фидбека. Каждое «это кринж» от пользователя → новый пункт (или
  усиление старого). Файл трекается — это накопленное определение вкуса.
- Критик (§12) обязан прогонять каждый план по чеклисту **и** по контексту:
  что уже съедено сегодня, что было вчера, время суток, наличие, сколько
  готовки план требует.
- Оценка пользователя первична: критик снижает частоту кринжа, но не заменяет
  фидбек. Спорные случаи — в CRINGE.md с пометкой.
